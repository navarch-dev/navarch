# M2: hub on one machine

Read `docs/DESIGN.md` (sections 3, 4, 8, 9 and 13) first.

## Deliverables

1. `navarch-store`: the `Store` trait, `FileStore` and `MemoryStore`, for every item in the table of section 8. Atomic writes. `tasks/index.toml` is derived: provide `rebuild_index()` and keep the index in step on every task write. Tests cover round trips, concurrent writers within one process, a corrupt card (reported, not fatal), and index rebuild.
2. `navarch-transport`: the `Link` trait, length-prefixed framing with the 1 MiB limit, `LocalLink` (Unix socket client and listener), an in-memory link pair for tests, and a reconnecting wrapper with jittered backoff. `RelayLink` is M3.
3. Reliable delivery on top of a link, shared by hub and worker (place it in `navarch-transport`): envelope send with ack tracking, resend after reconnect, de-duplication by envelope ID with a bounded memory. Property-style tests with a link that drops and reorders.
4. Identity: generate and load the Ed25519 identity key (file mode 0600) and derive `MachineId` per section 3. The key helpers live in `navarch-crypto`; the rest of `navarch-crypto` is M3.
5. `navarch-worker`: `navarch worker serve` connects the M1 `Worker` to the hub over `LocalLink`, sends a `ProbeReport` on connect and on `Probe`, and survives hub restarts.
6. `navarch-hub`:
   - `navarch hub serve`: accepts worker links, tracks online state, applies worker messages to the store and the inbox.
   - Control API on `hub.sock`: line-delimited JSON, one request type per tool in section 8, typed in a `control` module with serde tests.
   - `navarch hub mcp`: stdio MCP server using `rmcp`, one tool per control request, with input schemas and descriptions written for a model to read. It connects to `hub.sock` and reports a clear error if the daemon is not running.
   - Validation on `dispatch`: machine known, `active` and online; agent reported by that machine; `cwd` non-empty. The hub does not second-guess the worker's policy.
   - A local worker's machine is created `active` automatically on first connect over `LocalLink`. Remote machines (M3) start `pending`.
7. `navarch-cli`: `navarch hub serve`, `navarch hub mcp`, `navarch hub status`, `navarch hub tasks`, `navarch hub init` (writes commented example `projects.toml`, `routes.toml` and one role file; never overwrites).
8. `docs/hub.md`: how to start the hub and a worker on one machine, how to register `navarch hub mcp` as an MCP server in Claude Code, and each tool with an example call.

## Acceptance

- All three cargo checks pass.
- End-to-end test in one process with `FakeDriver`: start hub and worker over an in-memory link, `dispatch`, receive `Accepted` and `Finished`, `send_to_session`, `cancel` a running turn, escalate a permission and answer it through `answer_permission`, read the inbox, and see the task card and index reflect each step.
- Restarting the hub mid-turn does not lose the `Finished` message: the worker resends it and the card ends in the right state.
- With a real adapter (reviewer): from a Claude Code session with the MCP server registered, dispatch a small task to the local worker, then send a follow-up to the same session.

## Out of scope

Relay, pairing, encryption, remote workers.
