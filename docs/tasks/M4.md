# M4: completion events, direct links and packaging

Read `docs/DESIGN.md` first, in particular sections 2, 8, 9, 10, 12 and the new sections 8a ("Events for the orchestrator"), 9a ("Direct links") and 15 ("Packaging").

The same rules as earlier milestones apply: dependency rules of section 2, `#![forbid(unsafe_code)]`, no `unwrap`/`expect` outside tests, every variable-size message bounded, no cryptographic primitive implemented by hand. If a design detail turns out to be unsound or impossible, stop and write the problem and a proposed change in `docs/notes/m4-open-questions.md` instead of improvising. Do not commit.

## Deliverables

### A. Events for the orchestrator

1. Hub daemon: an in-process event bus (`tokio::sync::broadcast`, bounded) fed from the same place that appends to the inbox. One `HubEvent` per inbox entry: `seq` (monotonic, persisted with the inbox entry so it survives restarts), `kind` (`finished`, `failed`, `permission_ask`, `rejected`, `machine_pending`, `worker_online`, `worker_offline`), `card_id`, `step`, `machine`, `summary` (at most 200 characters), `time`. `machine_pending` is new: emitted when pairing stores a new pending machine. `worker_online`/`worker_offline` go to the bus only, not to the inbox.
2. Control API: a new request `subscribe { after_seq: Option<u64> }`. The connection then becomes a stream: the daemon first replays inbox entries with `seq > after_seq` that are still unread, then writes one JSON line per live event. A subscriber that falls behind the broadcast buffer receives one `lagged` line and must re-read the inbox; the daemon never blocks on a slow subscriber. Existing request/response behaviour on other connections is unchanged.
3. Control API and MCP tool `wait_for_events { timeout_secs (default 300, max 1800), after_seq }`: returns as soon as at least one unread inbox entry with `seq > after_seq` exists, otherwise when the timeout elapses with an empty list. It returns compact events only (`seq`, `kind`, `card_id`, `step`, `machine`, `summary`, `time`), never whole envelopes, and does not mark anything read (`read_inbox` still does). The tool description must tell a model when to use it (after dispatching, when it has nothing else to do) and that it returns early on new events.
4. `navarch hub mcp`: declares the experimental capability `claude/channel` and, when started with `--channel` (or `NAVARCH_CHANNEL=1`), subscribes to the daemon and sends one MCP notification `notifications/claude/channel` per `finished`, `failed`, `permission_ask`, `rejected` and `machine_pending` event. `params.content` is one or two plain sentences a model can act on (what happened, which card, which machine, and which tool to call next, for example `get_task` or `answer_permission`). For finished, failed, rejected and permission_ask, the text includes the bounded event summary as well as the next-tool hint. A new process uses atomic `subscribe_live` to start from the latest sequence without replaying unread history; the daemon sends a `ready` cursor before live events. `params.meta` carries `kind`, `card_id`, `step`, `machine` and `seq` as strings; keys use only letters, digits and underscores. Without `--channel` no notification is ever sent. If the daemon is down or restarts, the MCP process keeps running and resubscribes with backoff, resuming from the last `seq` it delivered (or the initial live baseline if no notification has been delivered).
5. `navarch hub watch`: a CLI command that subscribes and prints one readable line per event until interrupted (`--json` for raw lines). It is how a person, a script or another client follows the hub.
6. Tests: event emitted exactly once per inbox entry; replay from `after_seq`; `seq` continues after a daemon restart; lagging subscriber gets `lagged` and the daemon is not blocked; `wait_for_events` returns early and on timeout (`tokio::time::pause`); MCP server sends the channel notification only with `--channel`, with the exact method name and params shape, tested over a real stdio/duplex MCP session; resubscribe after the control socket drops.
7. Channel compatibility: Claude Code only registers a stdio server as a channel when the server negotiates an MCP protocol revision older than `2026-07-28` (or the user sets `MCP_PROTOCOL_NEGOTIATION=legacy`). Check which revision `rmcp` negotiates and record it in `docs/notes/m4-open-questions.md`; if `rmcp` can be pinned to an older revision when `--channel` is given, do that, otherwise document the environment variable. The capability value must be exactly `{}`. Claude Code sends no acknowledgement for a channel notification, so never wait for one.
8. `docs/hub.md`: a section "Getting told when work finishes" covering the three ways (channel, `wait_for_events`, `navarch hub watch`), with the launch command `claude --dangerously-load-development-channels server:navarch` (the server must also be registered under the name `navarch`), what the model sees (`<channel source="navarch" kind="finished" ...>`), and a note that channels are a Claude Code research-preview feature that needs a claude.ai or Console login and may change.

### B. Direct links

Design in section 9a. Summary of what to build:

1. `navarch-transport`: `DirectLink`, a TCP link that runs exactly the same nonce exchange, Noise KK handshake with the same prologue construction, and the same record chunking as `RelayLink`. Factor the shared part out of `relay.rs` into one module used by both; do not copy it. Framing on TCP: u32 big-endian length prefix, at most 1 MiB, as section 9. A `DirectListener` (hub side) and `DirectConnector` (worker side). Transient listener accept errors warn and back off 100 ms before retrying.
2. First bytes on a direct connection: a fixed magic `NAVARCH-DIRECT/1\n`, then the worker's hello frame with its `MachineId` and nonce. The hub looks up the machine; unknown, pending or revoked machines are dropped before any Noise processing, with no distinguishing reply. A 10-second deadline covers the whole handshake. Limit concurrent unauthenticated connections (64) and per-source-address attempts (10 per minute).
3. Hub: optional `[direct] listen = "0.0.0.0:7391"` in `hub.toml` (absent by default: no port is opened unless configured), and optional `advertise = ["192.168.1.20:7391"]`. When `advertise` is absent the hub advertises its non-loopback, non-link-local interface addresses with the listen port. After a worker's link is established over the relay (or directly), the hub sends a new envelope body `HubEndpoints { direct: Vec<String> }` (at most 8 entries, each at most 64 bytes). This travels inside the Noise channel, so only paired machines learn it and the relay cannot alter it.
4. Worker: stores the last `HubEndpoints` in its state directory. The connector used by the reconnecting wrapper becomes: try each stored direct address (connect timeout 2 s each, at most 3 addresses), and fall back to the relay. While connected through the relay, immediately attempt direct when an authenticated HubEndpoints announcement contains any address absent from the previous stored list, including the first announcement. Keep retrying direct every 5 minutes when endpoints are known in the background; on success, switch: the new link takes over and reliable delivery resends anything unacknowledged, exactly as after any reconnect. A worker config key `direct = false` disables direct links.
5. Hub side accepts a new authenticated link for a machine that already has one by replacing the old link (same rule as the relay's duplicate-connection replacement), so switching never leaves two live links for one machine.
6. `list_workers` and `navarch hub status` show how each worker is connected: `local`, `direct` or `relay`.
7. Tests: direct handshake success; unknown, pending and revoked machine dropped; replayed first message rejected; wrong magic; oversize frame; handshake deadline; both limits; fallback to relay when the direct address refuses or black-holes (use a listener that accepts and never answers); switch from relay to direct mid-turn with `FakeDriver` and the result arrives exactly once; hub restart with direct only (relay stopped) still reconnects; `HubEndpoints` bounds.
8. `docs/security.md`: add the direct listener to the threat table (a LAN attacker can connect to the port, can learn that a hub listens there, cannot complete a handshake, cannot learn which machines are paired). `docs/hub.md` and `docs/worker.md`: how to enable it.

No discovery protocol (mDNS or broadcast) in this milestone: addresses only travel inside the authenticated channel.

### C. Packaging

1. `navarch --version` prints the crate version and the git commit (short hash, `-dirty` when applicable) embedded at build time by a `build.rs` in `navarch-cli` that shells out to `git` and falls back to `unknown` without failing the build. Set the workspace version to `0.1.0`.
2. `navarch service install|uninstall|status <hub|worker|relay> [--listen <addr> for relay]`: writes and loads a per-user service that runs the corresponding `serve` command and restarts it on failure. macOS: a launchd agent plist in `~/Library/LaunchAgents/dev.navarch.<role>.plist`, loaded with `launchctl bootstrap gui/<uid>`. Linux: a systemd user unit in `~/.config/systemd/user/navarch-<role>.service`, enabled with `systemctl --user enable --now`. Logs go to `~/.navarch/logs/<role>.log` on macOS and the journal on Linux. The generated file embeds the absolute path of the current executable and `NAVARCH_HOME` when it is set. `--dry-run` prints the file and the commands without touching anything. File generation is a pure function with unit tests on both platforms' output; the commands that call `launchctl`/`systemctl` are thin and reported clearly when they fail. Put this in `navarch-cli` (module `service`), not in a new crate.
3. `.github/workflows/release.yml`: on a tag `v*`, build `navarch` in release mode for `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, package each as `navarch-<version>-<target>.tar.gz` containing the binary, `LICENSE` and `README.md`, write `SHA256SUMS`, and attach everything to a GitHub release. Third-party actions pinned by full commit SHA; `permissions: contents: write` only on the release job.
4. `install.sh` at the repository root: POSIX `sh`, detects OS and architecture, downloads the matching tarball and `SHA256SUMS` from the latest GitHub release (or `NAVARCH_VERSION`), verifies the checksum, installs to `${NAVARCH_INSTALL_DIR:-$HOME/.local/bin}`, and prints what to add to `PATH` if needed. It never uses `sudo`, never pipes to a shell, fails closed on a checksum mismatch, and passes `shellcheck`.
5. (Dropped during review: no container image. The relay is one binary; `navarch service install relay` covers running it.)
6. `docs/install.md`: install from a release, from source, as a service; upgrading; uninstalling. `README.md` and `README.zh-CN.md` quick start updated to match (keep both in step).
7. Release profile in the workspace `Cargo.toml`: `lto = "thin"`, `codegen-units = 1`, `strip = true`, `panic = "abort"` only if no code relies on unwinding (check, and say which you chose in the notes).

## Acceptance

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` pass.
- End-to-end test in one process: relay, hub with a direct listener on loopback, worker with `FakeDriver`. The worker first connects through the relay, receives `HubEndpoints`, switches to direct; a dispatch started before the switch finishes exactly once after it; a subscriber sees `worker_online`, `finished` in order with increasing `seq`.
- `navarch service install hub --dry-run` prints a valid plist on macOS and a valid unit on Linux (tested by parsing in unit tests).
- `sh -n install.sh` passes; if `shellcheck` is installed it passes too.
- Manual (reviewer): with a real adapter, a Claude Code session started with the channel receives a completion event without polling; a worker switches from relay to direct on one machine; `navarch service install` runs the hub under launchd.

## Out of scope

mDNS or any unauthenticated discovery, NAT traversal, hosted relay accounts, Homebrew or other package-manager formulas, Windows, an independent security audit.
