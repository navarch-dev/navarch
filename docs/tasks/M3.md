# M3: relay, pairing and encryption

Read `docs/DESIGN.md` (sections 3, 9, 10, 11, 12 and 13) first.

Use well-known crates for every primitive (`ed25519-dalek`, `x25519-dalek`, `spake2`, `snow`, `chacha20poly1305`, `blake2`, `rand`). Do not implement cryptographic primitives. If a design detail turns out to be unsound or impossible with these crates, stop and write the problem and a proposed change in `docs/notes/m3-open-questions.md` instead of improvising.

## Deliverables

1. `navarch-crypto`:
   - X25519 static key generation and storage next to the identity key.
   - Pairing state machines for both sides per section 10: code generation and parsing, SPAKE2, key confirmation over the transcript, encrypted exchange of public keys and display names. Pure state machines: bytes in, bytes out, no I/O.
   - Noise KK channel wrapper: handshake as initiator and responder, then `seal` and `open`, with rekey left to `snow` defaults.
   - Tests: success, wrong secret, replayed message, tampered ciphertext, truncated frames, mismatched static keys, expired code.
2. `navarch-relay`: the server from section 11, with challenge authentication, routing, pairing rooms, limits, and structured logs. `navarch relay serve --listen <addr>`. A `/healthz` endpoint. Tests with real WebSocket clients on loopback: routing, offline error, replacement of a duplicate connection, room expiry, room closed after a failed confirmation, each limit.
3. `navarch-transport`: `RelayLink`, which authenticates to the relay, runs the Noise handshake with the peer, and then implements `Link`. Plugged into the existing reconnecting wrapper and reliable delivery from M2 without changes to hub or worker logic.
4. Hub: `navarch pair [--relay <url>]` prints the code and waits; on success stores the machine as `pending`. `approve_machine` and `navarch hub machines [approve|revoke] <id>`. The hub keeps a relay connection, accepts Noise handshakes only from known machines, and ignores non-`active` ones. Relay URL in `hub.toml`.
5. Worker: `navarch join <code> --relay <url>` stores the hub's keys and the relay URL, then `navarch worker serve` connects through the relay when no local hub socket is configured.
6. `docs/relay.md` (running a relay, behind TLS) and `docs/security.md` (the table from section 12 expanded: assumptions, what is and is not protected, how to revoke a machine).

## Acceptance

- All three cargo checks pass.
- End-to-end test in one process over loopback: relay, hub and worker with `FakeDriver`; pair with a code, approve, dispatch, send, cancel; drop the worker's connection mid-turn and verify the result still arrives exactly once.
- A second client using the same room with a wrong secret fails, and the room is closed for the right code too.
- A client that was never approved cannot get any message accepted by the hub.
- The relay test asserts that payload bytes never appear in relay logs.
- Manual (reviewer): two machines, or two `NAVARCH_HOME` directories on one machine with a relay on loopback, complete pairing and one real dispatch.

## Out of scope

Direct LAN connections, hosted relay accounts, packaging.
