# M5: the hub is driven from the command line; MCP is removed

Read `docs/DESIGN.md` first (sections 2, 8, 8a), then `docs/hub.md` and `crates/navarch-hub/src/control.rs`.

Decision: the orchestrator no longer reaches the hub through an MCP server. It runs `navarch hub ...` commands (an agent session does this through its shell tool; a person or a script does the same). The control API on the hub socket stays the single interface; the CLI is a thin client of it.

The same rules as earlier milestones apply: dependency rules of section 2, `#![forbid(unsafe_code)]`, no `unwrap`/`expect` outside tests, every variable-size input bounded. If a detail turns out to be unsound, stop and write the problem and a proposed change in `docs/notes/m5-open-questions.md` instead of improvising. Do not commit.

## Deliverables

### A. Remove the MCP server

1. Delete `navarch hub mcp`, `crates/navarch-hub/src/mcp.rs`, `crates/navarch-hub/src/mcp/`, the channel notification code and their tests. Remove the `rmcp` dependency from the workspace and from `navarch-hub` (and any dependency that only it needed). `Cargo.lock` must shrink accordingly.
2. Keep everything on the control API, including `subscribe`, `subscribe_live` and `wait_for_events`. Keep `mcp_servers` in `Dispatch`: that field configures MCP servers for the *worker's agent session* and is unrelated to this change. The `mcp` permission kind in worker policy also stays.
3. Remove the phrase "one request per orchestrator tool" style comments that describe the control API in MCP terms; describe it as the hub's control API.

### B. Commands

All under `navarch hub`, all talk to the running daemon over the control socket, all accept `--json` (machine-readable, one JSON document on stdout, nothing else on stdout). Errors go to stderr. When the daemon is not running the message says so and names `navarch hub serve` and `navarch service install hub`.

| Command | Control request | Notes |
|---|---|---|
| `dispatch --machine <id> (--agent <name> \| --role <name>) --cwd <path> [--title] [--project] [--mode] [--model] [--card <card_id>] [--mcp-servers <json file>] [--wait [--timeout <secs>]] [PROMPT]` | `Dispatch` | Prompt from the positional argument, `--prompt-file <path>`, or stdin when the argument is `-` or absent and stdin is not a terminal. Exactly one source; at most 256 KiB; empty prompt rejected. Prints `card_id` and `task_id`. |
| `send <card_id> [PROMPT]` | `GetTask` then `SendToSession` | Resolves machine, agent and session from the card's latest step. `--machine` and `--session` (with optional `--agent`, `--card`) address a session directly instead. Same prompt sources and `--wait` as `dispatch`. |
| `cancel <card_id>` | `GetTask` then `Cancel` | Cancels the card's running step. `--task <task_id>` cancels one task directly. Nothing running: say so, exit 0. |
| `task <card_id> [--log]` | `GetTask` | Readable card: title, state, steps (role, agent, machine, session, state), result summary; full result text of the latest step. |
| `tasks [--all]` | `ListTasks` | Exists; keep. |
| `sessions [--machine] [--agent] [--cwd] [--limit]` | `ListSessions` | |
| `inbox` | `ReadInbox` | Prints unread entries and marks them read. `--peek` uses `WaitForEvents` with timeout 0 and `include_read: false`, returning only unread entries and marking nothing. |
| `wait [--card <card_id>] [--after-seq <n>] [--timeout <secs>]` | `WaitForEvents` (repeated as needed) | Blocks until an event arrives; with `--card`, until an event for that card that needs attention: `finished`, `failed`, `rejected` or `permission_ask`. Uses `include_read: true` so replay depends only on the sequence cursor. Prints the outcome and the last `seq`. Marks nothing read. |
| `permission <request_id> (--choose <option_id> \| --cancel)` | `AnswerPermission` | |
| `status`, `watch`, `machines`, `init`, `serve` | unchanged | |
| `guide` | none | Prints the orchestrator guide (deliverable C) to stdout. |

`--wait` on `dispatch` and `send`: after the request succeeds, behaves like `wait --card <card_id>` scoped to events newer than the sequence at dispatch time, then prints the outcome. `WaitForEvents.include_read` is optional and defaults to false for backwards compatibility; all CLI wait paths set it true. Readable card outcomes print `card_id`, `task_id`, `outcome`, `seq`, a blank line, then the full result or permission block without repeating the event summary. JSON output retains the events. For `finished` it prints the result text (the same text `task` shows). For `permission_ask` it prints the request ID, what is being asked, the offered options, and the exact `navarch hub permission ...` command to answer, then exits; the caller answers and runs `navarch hub wait --card <card_id> --after-seq <seq>` to continue.

Exit codes, documented in `--help` and in the guide, and identical for `wait` and `--wait`:

| Code | Meaning |
|---|---|
| 0 | Success; for a wait, the step finished |
| 1 | Usage error, daemon unreachable, or request rejected by the hub |
| 3 | The step failed, was rejected by worker policy, or was cancelled |
| 4 | A permission answer is needed |
| 124 | Timed out waiting (the task keeps running) |

No race between dispatching and waiting: take the event cursor before sending `Dispatch` (or use a cursor returned by the daemon; add an optional `seq` to the dispatch response if that is the clean way) so that an event emitted immediately after dispatch is never missed. A wait that outlives the control API's 1800-second cap re-issues the request with the latest cursor until `--timeout` elapses; `--timeout 0` on `wait --card` means no limit. If the daemon restarts during a wait, reconnect with backoff and continue from the last cursor.

Input bounds: prompt 256 KiB, title 200 characters, `--mcp-servers` file 64 KiB. Reject rather than truncate.

Put command parsing and rendering in `navarch-cli` (split `hub.rs` into a `hub/` module: `mod.rs`, `dispatch.rs`, `wait.rs`, `render.rs`, or similar; no file over about 400 lines). Rendering is pure functions with unit tests. Any logic that both `--wait` and `wait` need lives in one place.

### C. Orchestrator guide

Without MCP tool descriptions, an agent has to be told how to drive the hub. Provide:

1. `docs/orchestrator.md`: a short guide written for an agent to read (second person, imperative, under 120 lines). It covers: check `navarch hub status` to see machines and their agents; dispatch with `--wait` for short work; for long work dispatch without `--wait` and run `navarch hub wait --card <id> --timeout 0` as a background shell command so the session is told when it ends; how to answer a permission request and resume waiting; `send` to continue a session; `cancel`; hand-offs with `--card`; exit codes; always pass `--json` when parsing output. It must state that a worker's local policy decides what is allowed and that the orchestrator must not try to work around a rejection.
2. `navarch hub guide` prints that file (`include_str!`).
3. `docs/hub.md`: replace "Register MCP in Claude Code" and "Tools and example arguments" with "Driving the hub from an agent session": show an example one-line guide pointer for users to add to their own project instructions (do not create a repository-root `AGENTS.md`), plus a ready-to-copy skill file example (`SKILL.md` frontmatter with name and description, body pointing at `navarch hub guide`). Rewrite "Getting told when work finishes" around `--wait`, `wait` as a background command, and `watch`; remove the channel material entirely.

## Tests

- Argument parsing: prompt source exclusivity, bounds, `--agent`/`--role` exclusivity, `--wait` flags.
- Each command against a real in-process hub daemon with a `FakeDriver` worker over `LocalLink` (reuse the existing end-to-end helpers): dispatch then task shows the result; `dispatch --wait` exits 0 with the result text; a failing step gives 3; a permission ask gives 4 and the printed answer command, and answering then `wait --card --after-seq` reaches 0; timeout gives 124 (`tokio::time::pause` where it is not a real process test); `send <card_id>` continues the same session; `cancel <card_id>`; `inbox` marks read and `inbox --peek` does not; `--json` output parses and has stable field names.
- No missed event: a `FakeDriver` that finishes instantly, 50 dispatch-with-wait runs, all exit 0.
- Daemon restart during `wait`: the wait resumes and finishes.
- `navarch hub mcp` no longer exists (clap rejects it) and `cargo tree -p navarch-cli` has no `rmcp`.
- At least one test runs the built binary end to end (`assert_cmd` or `std::process::Command` on `CARGO_BIN_EXE_navarch`) for `dispatch --wait --json` and checks stdout and the exit code.

## Acceptance

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` pass.

## Out of scope
